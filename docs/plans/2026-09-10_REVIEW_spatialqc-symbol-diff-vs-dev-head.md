## Method

Both file pairs were parsed with `ast`, every top-level `def`/`class` extracted, docstrings stripped
recursively, and re-emitted through `ast.unparse` — so comments, docstrings, blank lines, line reflow
and quoting style cannot generate noise. Symbols were paired by name and diffed with `difflib`.
Reference `main` was diffed against port `run_image_qc` directly (the port splits the click decorators
into a thin `main` wrapper). CLI options were extracted by regex into `flag → default` records and
set-diffed. Output contract was extracted mechanically: all string constants filtered to output-file
extensions, all `df[...]` column accessors, and all dict-literal / subscript keys inside the six
metric-writing functions.

## Output contract deltas

**None.** All three extractions came back empty:

- **Output filenames** — every string constant matching an output extension (`.json`, `.csv`, `.parquet`, `.png`, `.pdf`, `.tif`, `.tiff`, `.gz`, `.h5`) is present in both `qc.py`/reference and both SNR files. Zero reference-only, zero port-only.
- **Dataframe columns** — every `df_grid_roi[...]`, `new_df[...]`, `nucleus_props[...]`, `df_work[...]`, `df_spatial[...]`, `df_cells_mapped[...]` accessor and every `'x' in df.columns` test matches across the union of both file pairs. Zero on either side.
- **Metric keys** — key sets are identical for `save_roi_qc_metrics`, `save_cell_qc_metrics`,
  `save_simple_qc_metrics` and `compute_whole_grid_stain_percentiles`.

One apparent exception is an artefact of the extractor and is **not** a contract change: for
`assess_raw_intensity_quality` the key-set diff reports `dapi`, `boundary`, `intrna` as "removed".
Those three literals were the _keys of the deleted `_yaml_keys` dict_
(`{'dapi': 'DAPI', 'boundary': 'boundary', 'intrna': 'intRNA'}`), which the extractor cannot
distinguish from output keys. The emitted metric keys are still written at runtime by
`stats[channel] = {...}` over the unchanged loop `[('dapi', ...), ('boundary', ...), ('intrna', ...)]`,
so `intensity_quality.dapi` / `.boundary` / `.intrna` all still appear in `roi_qc_metrics.json`.

The plan doc records `--stain-names` as "dropped by the port (spatialxe commit `a5241ec`)" with a
request to re-confirm against the dev-HEAD reference. Two corrections from this audit:

1. **The flag is still present in the port under test.** It appears in the click option list on both
   sides (which is why the option counts are 20 vs 21, the sole delta being `--device`) and in both
   function signatures — `ref_image_qc.py:13093` and `qc.py:12448`. Whatever `a5241ec` removed is not

## Verdict

**I found no difference that would make the two produce different numbers on the CPU path.**

The port is a faithful refactor of `origin/dev` cd87a5d. 102 of the 114 paired symbols in the main
module are byte-identical after docstring stripping, as are 17 of 37 in the SNR module, with the other
18 SNR symbols differing only in type annotations. Nothing present in the reference was dropped from
either file, and the output contract — filenames, dataframe columns and metric keys — is identical by
mechanical set-diff, not by inspection.

**On commit 8e9cd23 specifically, which you asked me to pin down: it changed no value.** It replaced
`np.where(total_c > 0, neg_c / total_c, np.nan)` with
`np.divide(neg_c, total_c, out=np.full(n_rois, np.nan), where=total_c > 0)`. `np.where` evaluates the
quotient for every element before selecting, so it performed the 0/0 division that emitted the warning
and then threw that element away in favour of the literal `np.nan`. The port simply never evaluates
those elements, having pre-filled `out` with `np.nan`. Both write `nan` where `total_c == 0` and the
same quotient elsewhere. Worth noting for the record: the suppressed warning was `invalid value
encountered` (0/0), not `divide by zero`, because `neg_c` counts a strict subset of `total_c` — so
`total_c == 0` forces `neg_c == 0`, and no `inf` was ever produced. The change is genuinely
cosmetic, and no NaN or zero that used to be produced has changed.

Everything else resolves as follows. Four items are pure packaging (import relocation, `open(path)`,
`sorted(glob)`, forward-ref annotations) plus the `main`/`run_image_qc` split that makes the analysis
importable without click. Two items are new but inert at their defaults: `--device` reduces to the
reference's exact `detect_gpu_ids()`-then-cap logic at `"auto"`, and `_yaml_channel_cfg` resolves to
the same sub-dict for every lookup the code actually makes, which I verified against the real
`bin/roi_image_qc_thresholds.yaml` (`DAPI`/`boundary`/`intRNA` at lines 36/104/130, matched by the
`"DAPI"`/`"boundary"`/`"intRNA"` call sites).

Two residual risks are real but out of reach of a CPU test, and I want to name them rather than bury
them:

1. **`cp.cuda.Device(gpu_id)` binding (9771f53) can change GPU results.** It is a no-op on one card,
   but on a multi-GPU host the reference folded consumers outside the owning device's context. This is
   a fix, so any change is toward correctness — but it means a multi-GPU reference run is not
   guaranteed to reproduce, and GPU/CPU equivalence should be checked on the _port_ rather than
   assumed from the reference.
2. **`_yaml_channel_cfg` converts a silent misconfiguration into a hard failure.** With the shipped
   YAML this never fires. If any deployment ships a `channels:` block missing one of the three
   channels, the reference quietly used `_INTENSITY_CRITICAL_DEFAULTS` and `intensity_warn=0.15`,
   whereas the port now raises `KeyError`. That is the intended behaviour, but it is a new failure
   mode for a config the reference tolerated — worth a glance at any non-default thresholds YAML in
   the pipeline before rollout.

For a regression test, the whole CPU pipeline should be bit-reproducible: the tile grid, all focus /
intensity / Laplacian columns, `focus_score_norm`, `roi_focus_score_threshold`, both GMM stages, the
tissue-mask statistics, every SNR component and the full contents of `roi_qc_metrics.json`,
`cell_qc_metrics.json`, `roi_blur_threshold.json`, `snr_metrics.json` and `SNR_roi_tx.parquet`. Every
function on those paths is in the byte-identical set. Any difference at all is a packaging defect —
an import that resolved to a different module, or a `params`/CLI wiring slip — not a numeric drift,
and it should be chased as such rather than absorbed into a tolerance.
